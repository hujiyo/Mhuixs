# 引用模型：HOOK、BHS 与所有权

> 实测日期：2026-10-05
> 相关代码：`src/lib/hook.h`、`src/lib/bignum.h`、`src/lib/list.h`、`src/registry.c`
> 实测数据：`sizeof(BHS) == 64` 字节，布局已满；`sizeof(HOOK) == 40` 字节

这份文档要回答的是一个反复出现、但一直没被写死的困惑：
**HOOK 和 BHS 到底谁管"引用"？要不要引入引用计数？**

---

## 1. 两层，不是竞争关系

| 层 | 是什么 | 职责 |
|---|---|---|
| **BHS** | 一个**值**（数据本身） | 承载数据：`type tag + union{ Data }` |
| **HOOK** | 一个**命名引用** | 给值起个名字，让外部能按名字找到它 |

HOOK 里有 `name`（名字）、`owner`/`group`/`pm_s`（权限）、`obj`（指向 BHS 的指针）。

**"HOOK 抢了 BHS 的饭碗"这个担心，可以这样拆解：**
两者不冲突，因为职责不同 —— HOOK 是"名字"，BHS 是"值"。
真正被混淆的是**第三个概念：引用关系**。而引用关系的计数必须记在
**被引用的那一端（BHS）**，理由是引用者不止 HOOK 一种。

---

## 2. 一个 BHS 可能被三类东西引用

1. **HOOK** —— 命名引用，可按名字全局查找
2. **别的数据结构** —— 嵌入式引用，LIST 的元素、TABLE 的单元格、
   KVALOT 的值，直接存 `BHS*` 指针
3. **C 代码里的局部变量** —— 临时借用

要同时管住这三类引用者，唯一的公共交汇点就是**被引用的那个 BHS 自己**。
所以：**引用计数如果要有，字段加在 BHS 上，不加在 HOOK 上。**

---

## 3. 为什么现在**不**引入引用计数

### 3.1 致命问题：环回收不了

引用计数的经典死穴是循环引用。而"数据结构之间互相引用"（最初的设计意图之一）
**恰恰是最容易成环的场景**：A 的单元格指向 B，B 指向 A。

此时即使指向它们的 HOOK 全部 drop，两者的计数仍各为 1，永久滞留内存。
引用计数在原理上就看不出来"这个环已经和外部世界断开了"。

要处理环，只有**追踪式回收**（标记-清除 / 分代 GC）。那是另一个量级的工程：
要么在回收时暂停扫描全图，要么写屏障配合增量标记。不是加一个字段能解决的。

### 3.2 一致性负担远高于当前的单一所有权

现在采用的是**单一所有权**：容器拥有元素，`list.h` 里把规则写死了。
每条规则只需在一处维护。

引用计数是**共享所有权**：每一次赋值、覆盖、移除都必须正确 inc/dec。
漏一处泄漏，多一处 double free。回看 2026-10-05 修掉的这几个 bug ——
`free_table` 不释放单元格、`kvalot_remove` 漏放 value ——
如果当时是引用计数模型，出错点会是三倍以上。

### 3.3 与现有深拷贝语义冲突

`hook_set_bhs()` 是**深拷贝**：挂到 HOOK 上的值与外面那个是两份独立对象，
所以"同一份数据被多处引用"这件事**现在根本不发生**。
引用计数没有用武之地。

要支持计数，得先把深拷贝改成"传指针 + 计数"，这会改变所有调用方的语义。

### 3.4 硬约束：BHS 装不下了

```
sizeof(BHS) = 64 字节，已占满：
  type(0-3) is_large(4-7) data(8-39) capacity(40-47) length(48-55) type_data(56-63)
```

加一个引用计数字段就要扩到 72 字节，打破"固定 64 字节"的设计。
（若真要加，可以从 `is_large` 挤：它是 `int` 却只存 0/1，白占 3 字节。
但那属于另一个议题。）

## 4. 考古发现：你当年的 `hook_id` 是对的方向

初版 `Mhuixs/mlib/Mhudef.h`（2025-01）里，HOOK 长这样：

```c
typedef struct HOOK{
    void* handle;
    HOOKTYPE type;
    RANK rank;
    OWNER_ID owner;
    GROUP_ID group;
    HOOK_ID hook_id;    /* ← 定义过，但全初版只出现在这一行，从未使用 */
    char* name;
}HOOK;
```

`hook_id` 代表一种**ID 引用**（间接）：数据结构里存 ID，通过注册表解析成对象。
而现在的实现是**指针引用**（直接）：数据结构里直接存 `BHS*`。

两种方式的差别是决定性的：

| | ID 引用（初版设想） | 指针引用（现状） |
|---|---|---|
| 引用计数 | 可行（ID 表能记录引用关系） | 需在对象上记，且环无解 |
| 落盘 | 直接写整数，天然可序列化 | 指针不能落盘，必须深拷贝展开 |
| 跨进程 / 未来网络化 | ID 稳定，可直接传 | 指针无意义 |
| 访问速度 | 要过一层注册表解析 | 直接解引用，最快 |

**当年的直觉是对的，只是没实现；后来转成指针，这些能力就一起丢了。**
这不是失误 —— 指针引用的速度优势在单机内存库里是实打实的。
只是要知道自己换掉了什么。

---

## 5. 当前决策

**采用显式所有权，不引入引用计数。**
一句话规则：**谁创建，谁销毁；存进容器就交出所有权；从容器取出就拿回所有权。**
细则写在 `src/lib/list.h` 的注释里（LIST / TABLE / KVALOT 同规则）。

共享（别名）这件事**暂时不做**。现在的做法是深拷贝 —— 语义清楚，代价是内存。

---

## 6. 将来真要做，按这个顺序

1. **先做"显式别名"，不计数。**
   提供一个命令让两个 HOOK 指向同一个 BHS，生命周期由**创建者**负责，其余引用是借用。
   单线程命令模型下这就够用了，且实现成本极低。
   这一步的目的是**验证需求是否真实存在** —— 如果没人真的需要别名，到此为止。

2. **需求被验证后，再上引用计数。**
   这时才知道谁是真的引用者。同时必须明确写出"不支持环"的限制，
   并给出检测办法（比如创建引用时做一次可达性检查，拒绝成环）。

3. **如果环无法避免，才考虑 arena 或追踪式 GC。**
   这不是"再加个字段"的量级，而是一次架构变更，需要单独评估。

**不要跳过第 1 步直接上第 2 步。** 引用计数最贵的不是字段和 inc/dec，
而是"从此以后每一处代码都必须记住这件事"。

---

## 7. 由此暴露的一个现成缺口

`drop`（`reg_unregister_hook`）目前只做 `hash_remove`，
**不释放 HOOK 对象，也不释放它持有的 BHS**。
在"显式所有权"模型下这是个明确的漏洞：注册表拥有 HOOK，drop 就该释放它。

反复 drop / 重建同名钩子会持续增长内存。
这条与本文档是同一件事的两面 —— 在引用计数缺席时，"谁拥有"必须处处明确。
